# Hosted deployment — Vercel and Render

The client is a static Next.js build on Vercel; the server runs as a Docker web
service on Render, described by [`render.yaml`](../render.yaml).

## Server (Render)

`render.yaml` is a blueprint — point Render at the repository and it reads the
service definition rather than needing manual configuration.

Set by the blueprint:

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` / `HOST` | `3001` / `0.0.0.0` |
| `TRUST_PROXY`, `WS_TRUST_PROXY` | `1` — Render terminates TLS in front of the app |
| `WS_JWT_SECRET` | generated by Render, never stored in the repository |
| `DB_PATH` | `/app/data/messenger.db` |

One variable is deliberately left unset (`sync: false`) and must be filled in
the Render dashboard:

- **`CLIENT_ORIGIN`** — the deployed client's origin. It drives the WebSocket
  Origin check, so a wrong value does not degrade gracefully: connections are
  refused.

### The free plan resets the database

Render's free plan has an ephemeral filesystem. Every deploy and every restart
starts from an empty SQLite file.

This is survivable by design — LUME is client-authoritative. Clients re-bind
their existing Ed25519 identity on next unlock and re-upload prekeys, with no
new identity and no safety-number change, so conversations continue.

What does **not** survive: undelivered messages and uploaded files.

For durable server state, move to a paid plan with a `disk:` mount, or managed
storage. The trade-off is recorded against `SEC-20260621-015`.

## Client (Vercel)

Project root is `client/`. Vercel detects Next.js; no custom build command is
needed.

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_API_URL` | the Render service URL |
| `NEXT_PUBLIC_WS_URL` | the same host with `wss://` and the `/ws` path |

Both are compiled into the bundle and publicly readable — nothing secret goes
here. Because they are build-time values, **changing them requires a redeploy**;
editing them in the dashboard alone changes nothing.

## Order of operations

The two sides reference each other, so first deploys go:

1. Deploy the server on Render, note its URL.
2. Deploy the client on Vercel with that URL in both `NEXT_PUBLIC_` variables.
3. Set `CLIENT_ORIGIN` on Render to the Vercel origin, and let it redeploy.

Skipping step 3 produces a client that loads and then fails to open a
WebSocket — the Origin check rejects it. That symptom looks like a broken
server; it is a missing variable.
